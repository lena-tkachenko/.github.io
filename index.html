First-day onboarding in a CRM

Takes a new sales rep from first login to their first saved lead, without a training session.

  • Smart Walk-Thru
  • ShoutOut
  • Onboarding Tasks
  • SmartTips
Built on

The problem

New reps get a login and a long PDF. On day one they don’t know where to start, so they ask colleagues the same questions and save leads with missing fields.

What I built

  1. A welcome ShoutOut on first login that offers a two-minute start, with an option to skip.
  2. A Smart Walk-Thru that creates the first real lead step by step, explaining each required field.
  3. SmartTips on key fields that explain the expected format right where it’s needed.
  4. An Onboarding Tasks checklist that marks “Create your first lead” as done when the record is saved.

Why it’s built this way

The welcome shows once and can be dismissed, because forced tours get closed on reflex. The walkthrough does real work instead of a demo click-through, so at the end the rep has an actual lead. The checklist lets people come back later instead of finishing everything on day one.

One click, ten steps

A launcher that creates a standard record and runs the repetitive steps for the user, ending with a clear success message.

  • Launcher
  • Automated steps
  • Wait-for conditions
  • Error handling
Built on

The problem

Creating a standard record, such as a quote or an internal request, takes more than ten clicks: open the form, pick a template, fill the same fields, save. People make mistakes in exactly these boring, repetitive parts.

What I built

  1. A launcher next to the list view that starts the whole process in one click.
  2. A Smart Walk-Thru of 8–10 automated steps that opens the form, fills default values, selects options and moves between screens.
  3. Wait-for conditions between actions, so automation continues only when the page has actually loaded.
  4. A pause before saving, where the user reviews the filled form and confirms.
  5. A success message with a link to the new record, and a fallback to manual guidance if any step fails.

Why it’s built this way

I automate only the steps that are the same every time and leave decisions to the person. Waiting for elements instead of fixed delays keeps the flow reliable on slow connections. The fallback matters most: if the page changes, the user gets guidance instead of a silent failure.

A design system for in-app guidance

One theme for every tooltip, modal and launcher, so guidance looks like part of the product.

  • Global theme
  • CSS
  • Templates
  • Accessibility
Built on

The problem

When several builders create content, each tooltip ends up with its own colors, fonts and buttons. Guidance starts to look like a layer of ads on top of the app, and people learn to ignore it.

What I built

  1. Design tokens for color, type, spacing and corner radius, taken from the host app’s own interface.
  2. Reusable templates for tooltips, step balloons, modals and banners, with consistent buttons and step counters.
  3. Global CSS that applies the theme everywhere, so one change updates all content.
  4. Accessibility checks: text contrast of at least 4.5:1, visible focus states and keyboard navigation.
  5. A before-and-after comparison on the same flow.

Why it’s built this way

This is where my UX background pays off. A shared system makes content faster to build and easier to maintain, and guidance that matches the product feels trustworthy rather than intrusive.

AI that checks what people type

An AI SmartTip that reviews a free-text field and tells the user what’s missing before they submit.

  • AI SmartTip
  • Prompt-based validation
  • UX writing
Built on

The problem

Support requests arrive with descriptions like “doesn’t work”, and the first reply is always a request for details. Classic validation can check that a field isn’t empty, but not whether the text is actually useful.

What I built

  1. An AI SmartTip on the description field of a request form.
  2. A validation prompt that checks for three things: what happened, where in the app, and when it started.
  3. A short, friendly hint that names exactly what’s missing, shown only when something is.
  4. A test run on good and bad sample descriptions before publishing.

Why it’s built this way

AI fits here because the rule is about meaning, not format. I kept the prompt narrow so its answers stay predictable, and tested it against examples first, because an AI check that misfires annoys people faster than no check at all.

Launching a feature and measuring adoption

A targeted announcement, a short walkthrough and a one-question survey, with tracking that shows whether people actually use the new feature.

  • ShoutOut
  • Smart Walk-Thru
  • Survey
  • Tracked events
Built on

The problem

A new feature ships, gets a line in a release email, and most people keep working the old way. Without data, nobody knows whether the change landed.

What I built

  1. A ShoutOut that appears in context, on the page where the feature lives, not at login.
  2. A three-step Smart Walk-Thru launched from the ShoutOut.
  3. A one-question survey after the first use: “Was this easier than before?”
  4. Tracked events on the feature’s main button, so adoption can be compared week by week.

Why it’s built this way

Announcements work best at the moment of need, and they should stop once they’ve done their job. I capped how often the ShoutOut appears and hid it from people who already use the feature. Measurement is part of the build, not an afterthought.

Making a tour survive UI changes

Replacing fragile auto-captured elements with stable selectors, and testing the tour the way QA tests a release.

  • DOM analysis
  • XPath
  • QA test cases
Built on

The problem

Enterprise apps generate dynamic IDs and re-render parts of the page. A tour that works today breaks after the next release, and users see a balloon pointing at nothing.

What I built

  1. An audit of every step’s element: which attributes stay the same and which change on reload.
  2. Custom XPath selectors anchored to stable attributes and visible labels instead of generated IDs.
  3. A test matrix covering user roles, screen sizes, and empty versus filled states.
  4. A short QA checklist I run before every publish.

Why it’s built this way

Stable guidance is invisible work, and it’s where my QA experience shows. Nobody notices a tour that keeps working, but everyone notices one that breaks.

Preventing errors before Save

Inline hints and validation that catch mistakes in a form before the user saves it.

  • SmartTips
  • Validation
  • Conditional rules
Built on

The problem

Records get saved with wrong formats and missing values, and someone has to clean them up later.

What I built

  1. Validation SmartTips for formats such as email, phone numbers and dates.
  2. Conditional hints that appear only for certain values, for example when a deal is marked as won.
  3. Messages written as instructions, not error codes.

Why it’s built this way

Fixing an error inline costs the user seconds; fixing it later costs someone else much more. Every message says what to do, not just what went wrong.
